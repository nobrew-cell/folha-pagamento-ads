Princípios da arquitetura

Antes de entrar nas camadas, vale entender as decisões que moldaram o sistema como um todo. Cada camada existe porque esses princípios exigem que ela exista — e não o contrário.

Separação de responsabilidades
Cada camada faz exatamente o que o nome dela diz, e nada além disso. A interface não calcula. O serviço não persiste. O repositório não valida regras de negócio.
TSV como fonte única
O database.tsv é a única fonte de verdade. Tudo o que existe em memória foi carregado dele. Tudo o que precisa durar é salvo nele. O XLS é derivado — nunca lido.
Portabilidade total
Nenhuma dependência externa. Apenas a biblioteca padrão do Java. O sistema roda em qualquer máquina com JDK 17+ sem instalação adicional.
Configuração como dado
Salário-base, teto de bônus e outros parâmetros são persistidos no TSV via linha #CONFIG. Não existem arquivos de configuração separados nem constantes estáticas.
Segurança por sessão
A separação entre perfil Funcionário e Administrador é feita na abertura de cada sessão. A segurança do ambiente (acesso à máquina) é responsabilidade da empresa.
Registro contínuo de operações
Toda operação relevante é registrada em arquivo de registro mensal. O registro nunca interrompe o sistema — falhas de escrita são silenciosas.

Fluxo entre camadas

Direção das dependências no fluxo de chamadas em tempo de execução: ui chama service, que chama repository, que acessa o arquivo. Nenhuma dessas camadas chama a camada acima dela em tempo de execução.

Isso não é uma regra absoluta de imports — main importa todas as camadas para montar as dependências, e util é transversal, acessado diretamente por main e service. A regra se aplica ao fluxo de dados e operações, não à estrutura de pacotes.

ui
ConsoleUI · SeletorPerfil · DashboardBI
↓ chama
service
FolhaService — regras de negócio e configurações
↓ chama
repository
FuncionarioRepository — leitura e escrita de arquivos
↓ lê / escreve
TSV
database.tsv — estado persistido em disco

O main é o ponto de montagem: instancia o repositório, injeta no serviço e injeta o serviço na UI. Depois disso, sai do caminho. O util é transversal — acessado diretamente pelo main e pelo service, sem passar por outras camadas.

Fluxo de inicialização

Sequência desde o main() até a abertura do menu. Três cenários são detectados antes de qualquer interação com o usuário.

entrada
SistemaFolha.main() — cria leitor de entrada com UTF-8 explícito
detectar
verifica database.tsv + pasta logs/ → três casos:
① sem banco + sem registros → primeiro acesso → força perfil Administrador
② sem banco + com registros → banco apagado acidentalmente → bloqueia e encerra
③ com banco → fluxo normal
carregar
FolhaService instancia FuncionarioRepository e chama carregar() — lê TSV, parseia #CONFIG e desserializa funcionários
perfil
SeletorPerfil.selecionar() — tela de escolha Administrador / Funcionário (pulada no primeiro acesso)
menu
ConsoleUI.iniciar() — laço principal até o usuário digitar 0 para sair
encerrar
service.salvar() → LoggerUtil.logEncerramento() → fecha o leitor de entrada

Camada model

Hierarquia de herança dos tipos de funcionário. Funcionario define o contrato abstrato; as subclasses implementam os cálculos específicos de cada tipo.

A
Funcionario abstrata
br.com.folha.model

Classe base de todos os funcionários. Campos imutáveis: nome e matricula. Define formatação monetária pt-BR e utilitários de normalização de nomes.

Contrato abstrato

getTipo()Retorna o identificador do tipo: "Padrao", "Comissionado" ou "Producao".
calcularSalarioFinal(double)Cada subclasse implementa sua fórmula. Recebe o salário-base como parâmetro — sem dependência de estado estático.
getDetalheExtra()Linha de detalhe exibida na folha (extras, comissão, bônus de produção).
toTSV(double)Serialização para linha do arquivo TSV.
toXLS(double)Serialização para linha HTML usada no relatório XLS.

Utilitários de nome

normalizarNome(String)Capitaliza cada palavra mantendo acentos — usado no armazenamento.
removerAcentos(String)Remove diacríticos via Normalizer.Form.NFD — usado na exibição no terminal para contornar limitações de codificação.
Nota Salário-base e teto de bônus não vivem nesta classe. São responsabilidade do FolhaService e persistidos na linha #CONFIG do TSV. Essa separação permite reconfigurar os valores sem precisar recriar os objetos de funcionário.
P
FuncionarioPadrao
extends Funcionario

Tipo mais simples. Salário final = salário-base. Sem campos adicionais. getDetalheExtra() retorna R$ 0,00.

C
FuncionarioComissionado
extends Funcionario

Campos adicionais: vendas e percentualComissao. Fórmula: salárioBase + (vendas × percentual / 100). A comissão não tem teto — é ilimitada por definição desse tipo.

P
FuncionarioProducao
extends Funcionario

Campos adicionais: quantidadeProduzida e valorPorPeca. O bônus de produção tem teto configurável.

Sobrecargas de calcularSalarioFinal

calcularSalarioFinal(base, teto)Versão correta para uso em produção. Recebe o teto absoluto do FolhaService e aplica Math.min(bônus, teto).
calcularSalarioFinal(base)Sobrecarga de compatibilidade com o contrato abstrato. Calcula sem teto. Não deve ser usada para exibição em folha nem para exportação.
Atenção Sempre usar FolhaService.calcularSalarioFinalCompleto() para obter o salário de um funcionário de produção com o teto corretamente aplicado. A sobrecarga sem teto existe apenas para satisfazer o contrato da classe abstrata.

Camada service

S
FolhaService
br.com.folha.service

Camada de negócio e ponto central do sistema. Instanciado pelo main e injetado no ConsoleUI. Detém as configurações de execução — salarioBase, tetoBonusPercentual, limiteMaximoMatricula e modoSequenciaRigido — carregadas do TSV na inicialização e persistidas imediatamente a cada alteração.

Cadastros e cálculos

cadastrar*()Três métodos, um por tipo. Normalizam o nome antes de adicionar à lista e chamam salvar().
calcularSalarioFinalCompleto()Ponto único e correto para calcular salário de produção com teto. Os demais tipos passam por calcularSalarioFinal(base) normalmente.
calcularTotalFolha()Soma dos salários finais de todos os funcionários com teto aplicado.

Operações administrativas

editarFuncionarioCompleto()Permite trocar o tipo (Padrão ↔ Comissionado ↔ Produção) com revalidação completa das regras de negócio.
iniciarNovoMes(boolean)Salva histórico e limpa variáveis mensais. Com true: mantém cadastro base com zeros. Com false: limpa tudo.
resetar()Cria cópia de segurança, limpa o arquivo e depois a lista em memória — nessa ordem, para evitar inconsistência se a escrita falhar.
importarArquivo()Cria cópia de segurança do estado atual antes de substituir. Se a cópia falhar, cancela a importação por segurança.

Camada repository

R
FuncionarioRepository
br.com.folha.repository

Responsável exclusivamente pela leitura e escrita de arquivos. Não toma decisões de negócio — recebe dados prontos do FolhaService e os persiste, ou lê o arquivo e devolve um DadosCarregados.

Leitura

carregar()Lê database.tsv. Se não existir, retorna valores padrão (R$ 2.000,00 / teto 200%).
parseTSV(caminho)Método privado de leitura com compatibilidade retroativa: lê #CONFIG com menos campos usando padrões. Valida cada linha com número de colunas e tipos esperados.
DadosCarregadosClasse interna imutável — contêiner de retorno do carregar() com a lista de funcionários e as configurações.

Escrita

salvar()Escreve database.tsv com UTF-8 explícito via OutputStreamWriter.
exportar()Gera TSV em exportados/dados/ e XLS em exportados/relatorios/, ambos com registro de data e hora.
criarBackup()Salva estado atual em backups/backup_[prefixo]_[timestamp].tsv.
salvarHistorico()Cópia de fechamento de mês em historico/yyyy-MM_[mes]_[timestamp].tsv.

Camada ui

S
SeletorPerfil
br.com.folha.ui

Exibida no início de cada sessão. Retorna o enum Perfil — FUNCIONARIO ou ADM — passado ao ConsoleUI para controlar quais opções ficam visíveis. No primeiro acesso (sem banco de dados), retorna ADM diretamente sem exibir a tela.

C
ConsoleUI
br.com.folha.ui

A camada de maior esforço de desenvolvimento. Gerencia todo o fluxo de interação: menus, validações de entrada, exibição da folha e menu administrativo com 9 opções.

O terminal não é responsivo como uma interface gráfica — centralização de títulos, controle de comprimento de linhas e consistência visual foram todos desenvolvidos manualmente. O zero (0) funciona como cancelamento universal em qualquer campo de cadastro ou edição.

D
DashboardBI
br.com.folha.ui

Janela gráfica JavaFX independente. Acessível pela opção (9) do menu administrativo.

Comportamento

Execução paralelaRoda em linha de execução separada — o console permanece ativo e utilizável enquanto o painel está aberto.
Modo leituraNão altera o database.tsv. Dados carregados no início via leitura do TSV. Elimina risco de corrupção por acesso simultâneo.
IndependênciaFechar a janela não encerra o processo principal.

Abas

Papel O DashboardBI não é apenas visualização — é uma ferramenta de gestão. O ADM pode exportar blocos da Visão Geral como PNG para enviar à diretoria ou tesouraria, gerar relatórios mensais em TXT ou PNG, acompanhar todos os eventos do sistema e ajustar configurações de identidade da empresa sem tocar no terminal.
Visão GeralKPIs do mês (total da folha, headcount, maior salário, média). Gráfico de evolução dos últimos 6 meses, pizza de distribuição por tipo, comparação com o mês anterior, Top 5 salários, consistência dos dados e logs recentes. Exportável como PNG — selecionando quais blocos incluir.
FuncionáriosListagem completa com filtros por mês, tipo (Padrão / Comissionado / Produção), ordenação e busca por nome. Exportável como TSV para integração com ferramentas externas.
RelatóriosResumo textual gerado sob demanda para o mês selecionado: totais, ranking por salário, quebra por tipo. Exportável como TXT, PNG ou TSV anual — arquivos prontos para encaminhar à diretoria ou tesouraria.
AuditoriaConsulta completa ao histórico de logs do sistema (arquivos logs/yyyy-MM_log.log). Filtros por operação, mês e busca livre. Mostra até 500 eventos ordenados por data decrescente. Exportável como TSV. Permite rastrear qualquer alteração — cadastros, edições, resets, importações, configurações.
ConfiguraçõesExibe os parâmetros atuais do sistema lidos do database.tsv (salário-base, teto de bônus, limite de matrícula, modo de sequência) e os compara com os padrões de fábrica. Permite editar nome da empresa, usuário e perfil persistidos em config/dashboard.properties. Lista as pastas monitoradas pelo dashboard.

Camada util

L
LoggerUtil
br.com.folha.util

Sistema de registros mensais. Cada mês gera logs/yyyy-MM_log.log. Falhas de escrita são silenciosas — o registro de operações nunca deve interromper o sistema principal.

Papel crítico na detecção de estado: contemPrimeiroAcesso() é consultado pelo main para distinguir "sistema nunca foi iniciado" de "banco de dados apagado acidentalmente", acionando o bloqueio de segurança no segundo caso.

Correção UTF-8 O método log() usava FileWriter, que no Windows gravava com CP1252 — corrompendo nomes acentuados. Corrigido para OutputStreamWriter(stream, StandardCharsets.UTF_8) com anexação explícita em todos os pontos de escrita.

Persistência

O sistema usa dois formatos de arquivo com papéis distintos e bem separados.

TSV — dados operacionais
Fonte única de verdade. Contém configurações (#CONFIG), cabeçalho de colunas e um funcionário por linha. Carregado na abertura, salvo no encerramento e a cada operação que altera estado.

Compatível com Excel, LibreOffice e ferramentas de BI sem conversão. Legível em qualquer editor de texto.
XLS — relatório formatado
Arquivo HTML com extensão .xls — aberto diretamente pelo Excel sem instalação de biblioteca. Gerado a partir do TSV no momento da exportação. Nunca lido de volta pelo sistema.

Destinado à leitura humana: cores por tipo de funcionário, total da folha no rodapé.

Arquivos gerados em execução

database.tsvRaiz do projeto — estado atual da folha.
exportados/dados/Exportações TSV com registro de data e hora — integração com BI e Excel.
exportados/relatorios/Exportações XLS formatadas com registro de data e hora — leitura humana.
backups/Cópias de segurança automáticas antes de reset ou importação.
historico/Capturas de fechamento de mês — nomeadas por ano-mês.
logs/Registros mensais de operações — usados também na detecção de estado.
Privacidade Todos os arquivos gerados estão no .gitignore. Podem conter dados de funcionários — nomes, matrículas, salários. Mantê-los fora do repositório é uma decisão intencional de privacidade.

Operações de registro

Cada operação relevante gera uma linha no arquivo do mês corrente. Formato: yyyy-MM-dd HH:mm:ss | OPERACAO | detalhe.

OperaçãoQuando é gerada
PRIMEIRO_ACESSONa primeira execução, sem banco de dados. Marca que o sistema já rodou ao menos uma vez — consultado na detecção de estado.
INICIO_SESSAOA cada inicialização normal (com banco presente).
FIM_SESSAOAo encerrar, com total da folha e resultado do salvamento.
CADASTROAo cadastrar qualquer funcionário, com tipo, nome e matrícula.
EDICAOAo editar um funcionário individualmente.
REMOCAOAo remover um funcionário, com nome e matrícula.
EXPORTAo exportar, com os caminhos do TSV e do XLS gerados.
IMPORTAo concluir uma importação, com caminho e quantidade de registros.
IMPORT_BACKUPComplementar ao IMPORT — registra o caminho da cópia de segurança criada antes.
RESETAo resetar, com o caminho da cópia de segurança automática.
NOVO_MESAo fechar o mês — se copiou funcionários e caminho do histórico gerado.
CONFIGA cada alteração de parâmetro de configuração, com valor anterior e novo.
EDICAO_LOTEAo concluir edição em lote: tipo, quantidade editada e quantidade ignorada.
ERROErros não-fatais capturados pelo sistema (ex: falha de cópia de segurança).

Decisões arquiteturais

Cada linha documenta uma escolha consciente — incluindo os casos em que a escolha mais simples foi preferida à mais correta, com justificativa.

DecisãoJustificativa e implicações
Configurações no FolhaService Salário-base e teto de bônus eram constantes estáticas em Funcionario. Mover para o serviço eliminou dependência de estado estático e permite reconfigurar valores em tempo de execução sem recriar objetos.
TSV no lugar de CSV O separador original era ponto-e-vírgula (variante CSV brasileira). O problema é estrutural: valores monetários no Brasil usam vírgula como separador decimal — R$ 1.500,00 — o que colide diretamente com o delimitador CSV. Além disso, ferramentas de BI como Power BI importam CSV com lógica regional inconsistente entre instalações. O TSV elimina essa ambiguidade: nenhum valor monetário ou nome de pessoa contém tabulação, então o delimitador nunca conflita com os dados. O arquivo continua legível em qualquer editor de texto e abre corretamente no Excel e LibreOffice sem configuração regional.
TSV como fonte única de verdade O XLS é gerado a partir do TSV, nunca o contrário. Evita divergência de dados e mantém importação e exportação simples, verificáveis e independentes de biblioteca externa.
double para valores monetários BigDecimal seria o tipo correto em produção — elimina imprecisão de ponto flutuante em operações financeiras. Mantido nesta versão por simplificar a serialização TSV e o escopo do projeto. Anotado como dívida técnica para versões futuras.
Zero como cancelamento universal Qualquer campo aceita 0 para cancelar e retornar ao menu. Consistente em toda a interface — sem tecla especial, sem comando memorizado.
Segurança por sessão, não por senha Armazenar senha localmente em texto seria inseguro. A separação Administrador / Funcionário protege por sessão. A segurança do ambiente (controle de acesso à máquina) é responsabilidade da empresa. Em produção real, o menu administrativo exigiria autenticação própria.
UTF-8 explícito em toda entrada e saída FileWriter e leitores sem charset explícito usam o padrão da JVM — no Windows, CP1252, corrompendo nomes acentuados. Corrigido para OutputStreamWriter(stream, StandardCharsets.UTF_8) e Scanner(arquivo, StandardCharsets.UTF_8) em todos os pontos de leitura e escrita.
Nenhuma dependência externa Apenas a biblioteca padrão do Java. Facilita distribuição, elimina problemas de versão e mantém o projeto portável sem gerenciador de dependências.
Painel analítico em linha de execução separada O DashboardBI roda em paralelo para não bloquear o laço principal do console. Opera em modo leitura para eliminar risco de corrupção por acesso simultâneo ao TSV.

Limites intencionais do sistema

Esta seção existe para alinhar expectativas. Cada limitação abaixo é uma escolha de arquitetura — não uma falta.

  • Não há concorrência multiusuário
  • Não há persistência transacional
  • Não há autenticação real
  • Não há banco relacional
  • Não há lock de arquivo
  • Não há atualização em tempo real do DashboardBI
  • Não há criptografia de dados em repouso
  • Não há controle de acesso por perfil granular
  • Não há integração com sistemas externos (ERP, Ponto eletrônico)
  • Não há validação de CPF/PIS

Riscos conhecidos / dívida técnica

Registro de concessões e pontos de melhoria que merecem atenção em versões futuras.

  • double para valores monetários — BigDecimal seria o tipo correto
  • Ausência de lock de arquivo — risco de escrita concorrente se dois processos acessarem o TSV
  • Acoplamento parcial UI/service — ConsoleUI conhece regras de validação de entrada
  • Dashboard em snapshot — não reflete alterações feitas no console durante a mesma sessão
  • Ausência de testes automatizados — cobertura zero de unitários e integração
  • Ausência de serialização tipada — parse do TSV depende de índices posicionais
  • Sem migração de schema — alterações no formato do TSV exigem recriação manual

Invariantes do sistema

Regras globais que devem ser verdadeiras em qualquer estado válido do sistema — antes, durante e depois de qualquer operação.

  • matricula > 0 — todo funcionário possui matrícula positiva
  • database.tsv é autoridade máxima — nenhum dado em memória contradiz o arquivo
  • Registros nunca interrompem a execução — falhas de log são silenciosas
  • XLS nunca é lido — apenas escrito, nunca usado como entrada
  • Todo funcionário possui tipo válido — Padrão, Comissionado ou Produção
  • Exportação nunca altera estado — operações de leitura são imutáveis
  • Salário final de produção nunca excede salarioBase + tetoAbsoluto
  • Toda operação que altera estado é imediatamente persistida
  • A lista em memória sempre corresponde ao conteúdo atual do TSV após cada operação

Política de tolerância a falhas

Consolidação do comportamento do sistema diante de cenários de erro. Cada categoria define uma resposta previsível.

O que bloqueia o sistema

  • database.tsv ausente com registros de primeiro acesso nos logs — banco apagado acidentalmente
  • Importação de arquivo TSV com formato inválido ou colunas insuficientes
  • Falha ao criar cópia de segurança antes da importação — operação cancelada por segurança

O que falha silenciosamente

  • Escrita no arquivo de log — erro capturado, sistema segue normalmente
  • Criação de diretórios de exportação — se falhar, apenas notifica no console
  • Fechamento do DashboardBI — não afeta o processo principal

O que gera rollback parcial

  • Reset — backup é criado antes da limpeza; se a limpeza falhar, o backup permanece íntegro
  • Importação — backup é criado antes da substituição; se falhar, o estado anterior está preservado

O que cancela a operação

  • Digitação de 0 em qualquer campo — cancelamento universal
  • Matrícula duplicada durante cadastro — operação rejeitada
  • Tipo inválido durante edição — operação rejeitada com mensagem

O que gera backup automático

  • Reset do sistema — backups/backup_reset_[timestamp].tsv
  • Importação de arquivo — backups/backup_pre_import_[timestamp].tsv
  • Fechamento de mês — historico/yyyy-MM_[mes]_[timestamp].tsv
